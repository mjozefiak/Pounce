1 · Audit (om-ux-shape, Review mode)

Verdict: rethink the shell, keep the engines. Every feature works and is careful about privacy, but the app has no home: Settings is the only window, and the things a person returns to (meeting notes, dictation history) are reachable only through the launcher panel as a list mode. The Settings window is a 9–10 tab toolbar (tabs for Apps, Files, Clipboard History, Dictation, Meetings, plus General, Features, Permissions, Advanced) with panes up to 4 screens tall. Evidence: inspected running debug build in QA mode (Dictation and Meetings panes, screenshots) and read the code of every pane.

✅ Keep

Launcher panel and its list modes (fast, keyboard-first; stays the quick path). HUDs (capsule, glass, no activation). Welcome flow structure (one step at a time, Done or Skip). About window. Per-plugin enable switch and Result Order. Key-handling and failure rules (Keychain error ≠ reset). The meeting window’s content (notes with quotes, speakers, transcript, finish/regenerate actions) is good; it only needs a better home.

Evidence limits

Inspected: code of all panes, the running debug build (Dictation, Meetings panes), the brand prototype. Not inspected: running Files/Clipboard/Apps/General/Features/Permissions/Advanced panes and Welcome (read from code only); VoiceOver and real keyboard traversal (only described in the design notes); native fidelity (AppKit controls drawn in HTML); real data sizes (1000+ notes scrolling, long titles beyond the sample). No usage data exists (no telemetry), so “people will use a window” is an assumption.
