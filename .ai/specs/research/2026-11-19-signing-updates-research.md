## 1. TCC and code identity

**TCC tracks an app by its designated requirement (DR).**
- TN3127: "Most code has a designated requirement (DR) which is how the code identifies itself: It's the code's way of saying 'If you see me again, here's how you tell it's really me.'" and "macOS solves this problem by recording your app's DR in its database of apps authorized to access the microphone. Each time your app tries to access the microphone, macOS checks that this version of the app satisfies the original DR." — https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements
- Quinn (Apple DTS): "The signing identity is used as a component of the designated requirement (DR), and TCC uses the DR to track whether build N+1 of your program is the same as build N." — https://developer.apple.com/forums/thread/707177
- Whether the TCC row is keyed by bundle id + `csreq` exactly: Quinn declined to confirm the `access.csreq` implementation ("I'm not sufficiently up-to-speed on TCC's implementation to answer that question") — https://developer.apple.com/forums/thread/730043. So "bundle id + csreq blob in TCC.db" is **UNVERIFIED from Apple** (widely reported by third parties; `tccutil reset <service> <bundle id>` takes a bundle id: https://developer.apple.com/documentation/xcode/resetting-access-to-protected-resources-in-macos).

**Ad-hoc signature: grants are lost on every build.**
- TN3127: "Unsigned code has no DR. Ad hoc signed code, called Sign to Run Locally by Xcode, has a DR but it's tied to that specific version of the code. In both cases macOS can't reliably track the identity of the code." and "Without a DR, macOS can't track this authorization across versions of your app." The cdhash form: `cdhash H"ff19..."` "is satisfied only by code with a specific cdhash value."
- Quinn: "Ad hoc signed code does not include a stable DR, and thus macOS is unable to tell that version N+1 of your app is the 'same code' as version N." Recommendation: "Sign your code with a stable code-signing identity, ideally one issued by Apple ... Developer ID, for direct distribution". — https://developer.apple.com/forums/thread/795739

**Developer ID: DR = identifier + Apple anchor + Team ID.**
- TN3127 example: `anchor apple generic and identifier "com.example..." and (LeafIsMacAppStore or IssuerIsDeveloperID and LeafIsDeveloperIDApp and certificate leaf[subject.OU] = SKMME9E2Y8)`; "The `certificate leaf[subject.OU] = SKMME9E2Y8` term requires that the leaf certificate's Organization Unit field be SKMME9E2Y8. In a Developer ID certificate, this is where you'll find the Team ID." `anchor apple generic` "is satisfied by any code signed with any code signing identity issued by Apple."
- The DR names the Team ID, not a certificate hash, so it survives certificate renewal (INFERENCE, see question 4).

**Self-signed certificate: DR = identifier + hash of that certificate.**
- Apple's `codesign` source (`DRMaker::make` / `nonAppleAnchor` in the Security project): the DR always contains the identifier; for a non-Apple anchor it walks up the chain while the Organization matches the leaf and pins the hash of the certificate it stops at. For a one-certificate chain this is the self-signed certificate itself, i.e. `identifier "<bundle id>" and anchor = H"<SHA-1 of the cert>"` (displayed by `codesign -d -r-` as `certificate root = H"..."`). — https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_codesigning/lib/drmaker.cpp . The logic was read from source; the exact printed text form is **INFERENCE** (so the answer to "leaf certificate hash?" is: root/anchor hash, which for a self-signed cert is the same certificate). Verify on a real build with `codesign -d -r- Pounce.app`.
- TN2206 (archived, still the only Apple text on this): "Many parts of macOS do not care about the identity of the signer. (Gatekeeper is a notable exception.) They care only whether the program is validly signed and stable. Stability is determined through the designated requirement (DR) mechanism, and does not depend on the nature of the certificate authority used. The keychain system and parental controls are examples of such usage. Self-signed identities and homemade certificate authorities (CA) work by default for this case." and "one big downside in using a self-signed identity is that you will never be able to revoke it". — https://developer.apple.com/library/archive/technotes/tn2206/_index.html
- Consequences (INFERENCE from the DR form): grants persist as long as the bundle id and the exact same certificate (same bytes, so same key and same validity dates) are used. A regenerated certificate with the same name "Pounce Release" has a different hash, so every grant is lost. An expired self-signed certificate cannot be "renewed" without changing the hash. TN2206 suggests a way around this: sign with an own CA and an explicit DR "designated => anchor rootCert and identifier com.foo.bar"; "By using your own CA you gain the ability to issue new identities at will, since any signing identities issued from your CA will now satisfy the check."
- Caveats on macOS 15/26 for self-signed + TCC: no Apple statement found. **UNVERIFIED.** Secondary source (skhd.zig docs): "Permissions will now persist across rebuilds as long as you sign each new build with the same certificate", but replacing a binary in place can invalidate a grant, and "is not a guarantee that every macOS version will accept self-signed services". — https://raw.githubusercontent.com/jackielii/skhd.zig/main/docs/CODE_SIGNING.md
- TN2206 notes one subsystem that does care about trust: the Application Firewall ("Self-signed identities and self-created CA will not be verified as being valid for this check unless the verifying system has been told to trust them").

## 2. Keychain

- Two implementations (TN3137): "The file-based keychain uses access control lists (SecAccess). The data protection keychain uses keychain access groups, supplemented by an optional access control object (SecAccessControl)." SecItem "defaults to targeting the file-based keychain. To target the data protection keychain, set the kSecUseDataProtectionKeychain attribute or the kSecAttrSynchronizable attribute to true." "The file-based keychain is on the road to deprecation. It's not officially deprecated, but some of the APIs surrounding it are." — https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains
- ACL binding to the creating app is by DR (TN2206 table): "Free access to the keychain item by the creating application and tracked with its DR (No automatic tracking for custom ACLs)." — https://developer.apple.com/library/archive/technotes/tn2206/_index.html
- Prompt behaviour: "the system checks whether the calling app is among the entry's trusted apps. If so, the system grants access. Otherwise, the system prompts the user for confirmation. The user may choose to Deny, Allow, or Always Allow the access. In the latter case, the system adds the app to the list of trusted apps for that entry". — https://developer.apple.com/documentation/security/access-control-lists
- Update signed with the same identity: the new build satisfies the stored DR, so no prompt (INFERENCE from the two quotes above). Different identity (ad-hoc rebuild, new self-signed cert, self-signed -> Developer ID) or different bundle id: DR not satisfied, so the user gets the "wants to use your confidential information stored in ..." prompt with Deny / Allow / Always Allow; the item is not deleted. The exact dialog wording is **UNVERIFIED** from Apple docs (the three buttons are documented).
- Data-protection keychain needs entitlements authorised by a provisioning profile: "macOS builds the list of data protection keychain access groups available to your program from its code signing entitlements ... These entitlements must be authorized by a provisioning profile. Your program needs an app-like bundle structure in which to embed that profile." (TN3137). Profiles only authorise Apple-issued identities: "a profile can only authorise code signed with signing identity whose certificate was issued by Apple" (Quinn, https://developer.apple.com/forums/thread/730043). So a self-signed or ad-hoc app cannot use the data-protection keychain; a Developer ID app can, with a Developer ID provisioning profile (note from https://developer.apple.com/support/developer-id/ : "if your Developer ID provisioning profile expires, the app will no longer launch"; profiles made after 2017-02-22 "are valid for 18 years").

## 3. Changing bundle identifier and/or signing identity

| Thing | Bundle id change | Signing identity change (same bundle id) | Source / status |
|---|---|---|---|
| TCC grants | New identity, all grants lost, old rows stay as stale entries | DR no longer satisfied, grants lost; the stale row can make the Settings toggle look "on" while access is denied, so users may need to remove and re-add the app or run `tccutil reset` | Quinn, thread 785384 (below); stale-row symptom is from secondary reports, **UNVERIFIED** from Apple |
| Keychain (file-based) | DR differs, prompt per item (or migrate while the old identity can still read) | Same: prompt per item | TN2206 + ACL doc (INFERENCE) |
| UserDefaults | New domain = new bundle id; old `~/Library/Preferences/<old id>.plist` is not read. A non-sandboxed app can read the old domain with `UserDefaults(suiteName: "<old id>")` / `persistentDomain(forName:)` and copy it | Unaffected | Standard behaviour; not re-fetched from Apple docs in this run: **UNVERIFIED** here |
| Launch at Login (`SMAppService.mainApp`) | Registration belongs to the old app; the new app must call `register()` again, and the old item should be unregistered by the old build before the switch | **UNVERIFIED** | Apple's class reference only says `register()` "Registers the service so it can begin launching subject to user approval" — https://developer.apple.com/documentation/servicemanagement/smappservice . No Apple text on rename or re-signing found |
| Sparkle update across the change | See question 5: works if the EdDSA key is unchanged; the old bundle name must be kept or handled ("Put a copy of your .app (with the same name as the version it's replacing)") | Works with unchanged EdDSA key (source: `SUUpdateValidator`) | Sparkle docs / source |

**No supported way to migrate TCC grants.** Quinn (Apple DTS) on moving an app to a new Developer ID team: "I'm not aware of a good solution to this problem )-: The options that I am aware of are either highly dependent on implementation details, or not a good user experience (`tccutil reset`), or don't work for all privileges [1]. Probably the best option is to ship an entirely new app, that is, change the app's bundle ID. This will let your team-signed build start from a clean slate." Footnote: "local network privacy ... is not reset by `tccutil`." — https://developer.apple.com/forums/thread/785384

Design consequence: do the bundle id rename and the certificate change in one release (one re-grant for the user instead of two), and prefer a new bundle id over a new DR under the old id (clean slate, no stale rows).

## 4. Apple Developer Program, Developer ID, notarization, Gatekeeper

**Price and enrolment.**
- "The Apple Developer Program is 99 USD per membership year. Prices may vary by region and are listed in local currency during the enrollment process." Same fee for individuals and organisations. Individual: legal name ("Your name will be displayed as the seller name"). Organisation: "must be a legal entity", needs a D-U-N-S Number and a website on its own domain. — https://developer.apple.com/programs/enroll/
- Fee waiver: "Be a legal entity with a status as a nonprofit organization, accredited educational institution, or government entity; Not be an individual, sole proprietor, or single-person business; ..." — https://developer.apple.com/help/account/membership/fee-waivers/ . So an individual open-source maintainer is not eligible.

**What Developer ID + notarization gives.**
- "Digitally signing software with a unique Developer ID and including a notarization ticket from Apple lets Gatekeeper verify that the software is not known malware and has not been tampered with." — https://developer.apple.com/support/developer-id/
- Un-notarized apps since macOS 15: "In macOS Sequoia, users will no longer be able to Control-click to override Gatekeeper when opening software that isn't signed correctly or notarized. They'll need to visit System Settings > Privacy & Security to review security information for software before allowing it to run." — https://developer.apple.com/news/?id=saqachfa (2024-08-06)
- User steps (Apple Support): "After you've tried to open the app ... Open System Settings. Click Privacy & Security, scroll down, and click the Open Anyway button to confirm your intent to open or install the app. The warning prompt reappears and, if you're absolutely sure that you want to open the app anyway, you can click Open." — https://support.apple.com/en-us/102445 . The page (as fetched) does not state how long the button stays ("about an hour" in older versions) or that an admin password is asked: both **UNVERIFIED**. Nothing found that macOS 26 changed this flow further: **UNVERIFIED** for 26 specifically.

**Notarization requirements** (https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution):
- "Use a 'Developer ID' application, kernel extension, system extension, or installer certificate for your code-signing signature. (Don't use a Mac Distribution, ad hoc, Apple Developer, or local development certificate.)"
- "Enable the Hardened Runtime capability for your app and command line targets"; "Include a secure timestamp with your code-signing signature"; "Don't include the `com.apple.security.get-task-allow` entitlement with the value set to any variation of `true`"; "Link against the macOS 10.9 or later SDK"; valid signatures on all executables.
- So a self-signed app cannot be notarized at all.
- Entitlements (https://developer.apple.com/documentation/security/hardened-runtime): runtime exceptions `allow-jit`, `allow-unsigned-executable-memory`, `allow-dyld-environment-variables`, `disable-library-validation` ("whether the app loads arbitrary plug-ins or frameworks, without requiring code signing"), `disable-executable-page-protection`, `debugger`; resource access `com.apple.security.device.audio-input`, `device.camera`, `automation.apple-events`, etc. "Make sure to use only the entitlements that are absolutely necessary". None of the runtime exceptions is documented as blocking notarization (only `get-task-allow` is); that `disable-library-validation` passes notarization is therefore **INFERENCE**, and it weakens the hardened runtime. With Developer ID it should not be needed, because all embedded frameworks (Sparkle, llama) are re-signed with the same Team ID.
- Relevant today: a hardened-runtime app without a Team ID (self-signed/ad-hoc) cannot satisfy library validation for third-party frameworks; Sparkle's docs say "Otherwise, the system may not let your application load Sparkle if you attempt to sign to run locally" and "This is not an issue for distribution when you sign your application with a Developer ID certificate." — https://sparkle-project.org/documentation/

**notarytool, CI, stapling** (https://developer.apple.com/documentation/security/customizing-the-notarization-workflow):
- `xcrun notarytool submit <file> --keychain-profile "..." --wait`; `xcrun notarytool store-credentials`. Accepted containers: "disk images (UDIF format), signed flat installer packages, and ZIP archives. It processes nested containers as well".
- "The notary service generates a ticket for the top-level file that you specify, as well as for each nested file." So submitting the DMG covers the app inside.
- Stapling: "To attach a ticket to your app, bundle, disk image, or flat installer package, use the `stapler` tool." "While you can notarize a ZIP archive, you can't staple to it directly. Instead, run `stapler` against each item that you added to the archive."
- App Store Connect API key: `notarytool submit --key <AuthKey.p8> --key-id <id> --issuer <uuid>` (man page: https://keith.github.io/xcode-man-pages/notarytool.1.html ; TN3147: "there's no need to supply your Apple ID because notarytool works that out based on the issuer" — https://developer.apple.com/documentation/technotes/tn3147-migrating-to-the-latest-notarization-tool). A forum thread says individual (per-user) API keys cannot use notarytool, a team key is needed (https://developer.apple.com/forums/thread/768634) — secondary, **UNVERIFIED**.
- Recommended order (INFERENCE from the above): sign app (hardened runtime, timestamp) -> build DMG -> sign DMG -> notarize DMG -> `stapler staple` the DMG. For a Sparkle zip: notarize, staple the `.app`, then zip.

**Certificate expiry and renewal.**
- "As long as your Developer ID certificate was valid when you compiled your app, then users can download and run your app, even after the expiration date of the certificate. However, you'll need a new certificate to sign updates and new applications." "You can create up to five Developer ID Application certificates". "Required role: Account Holder." Revocation: "can no longer be installed nor launch if it's already installed." Membership lapse: "users can still download, install, and run your applications that are signed with Developer ID". — https://developer.apple.com/support/developer-id/
- The 5-year validity of a Developer ID Application certificate was not stated on the pages fetched: **UNVERIFIED** (commonly cited).
- Does renewal change the DR? The default Developer ID DR checks `anchor apple generic`, the Developer ID issuer/leaf marker OIDs and `certificate leaf[subject.OU] = <Team ID>` (TN3127; also `DRMaker::appleAnchor` in Apple's source), not the certificate hash or dates. A renewed certificate of the same team therefore satisfies the same DR: **INFERENCE** (Apple does not say it in one sentence). Moving to a different team changes the DR (thread 785384).

- Security fixes in 2026: 2.9.5 (2026-08-02) and 2.9.6 (2026-08-17) hardened delta patching and the installer; pin at least 2.9.6, in practice 2.10.1.

**Setup for a non-sandboxed app** (https://sparkle-project.org/documentation/):
- SwiftPM: package URL `https://github.com/sparkle-project/Sparkle`; it is a binary target (`Sparkle-for-Swift-Package-Manager.zip`, checksum in `Package.swift`, `platforms: [.macOS(.v12)]`). Tools: "you will find Sparkle's tools to generate and sign updates in `../artifacts/sparkle/Sparkle/bin/`" (in a plain SwiftPM build: `.build/artifacts/sparkle/Sparkle/bin/` — that exact path is **INFERENCE**). The release tarball `Sparkle-2.10.1.tar.xz` also contains `bin/`.
- `./bin/generate_keys` stores the private key in the login Keychain and prints the public key for `SUPublicEDKey`; `-x` exports, `-f` imports (for CI use `generate_appcast --ed-key-file -` to read the key from stdin).
- `SUFeedURL` in Info.plist; an incrementing `CFBundleVersion`.
- Non-sandboxed apps do not need the XPC services (`SUEnableInstallerLauncherService`: "Don't enable for non-sandboxed apps") and may remove them.
- With SwiftPM-only packaging (no Xcode archive) the app's script must copy `Sparkle.framework` into `Contents/Frameworks` and sign its nested helpers (Autoupdate, Updater.app, XPC services) inside-out; the docs only say "Using Xcode's Archive Organizer will ensure Sparkle's helper tools are code signed properly". Exact manual signing order: **UNVERIFIED** from docs.

**What Sparkle verifies; Developer ID or not.**
- Docs: "Notarize and code sign the application via Apple's Developer ID program (if possible)." Developer ID is recommended, not required. EdDSA: "Sign the published update archive (dmg, zip, etc), binary delta updates, and installer packages with Sparkle's EdDSA".
- Source (`SUUpdateValidator.m`, `SUCodeSigningVerifier.m`, branch 2.x): the download is checked against the old app's EdDSA key; separately, if the old bundle is code signed, the old bundle's designated requirement is evaluated against the new bundle (`SecCodeCopyDesignatedRequirement(oldCode...)` then `SecStaticCodeCheckValidityWithErrors(newCode, ..., requirement)`). Decision: "Either DSA must be valid, or Apple Code Signing must be valid"; "We allow failure of one of them, because this allows key rotation without breaking chain of trust." Policy checks: a signed old app cannot be updated to an unsigned one; keys can be rotated but not removed. — https://github.com/sparkle-project/Sparkle/blob/2.x/Sparkle/SUUpdateValidator.m , https://github.com/sparkle-project/Sparkle/blob/2.x/Autoupdate/SUCodeSigningVerifier.m
- Consequences (INFERENCE from the source):
  - Ad-hoc app: the DR is a cdhash, so the code-signing check never matches; every update must pass EdDSA. Works, but EdDSA is the only trust anchor.
  - Self-signed app with a stable certificate: both checks pass.
  - Changing the certificate or the bundle id (identifier is part of the DR): code-signing check fails, the update is accepted only through the unchanged EdDSA key. So the EdDSA key must not change in the same release as the identity.
  - Gatekeeper pre-scan (`gktool scan`, macOS 14.4+) is only a launch warm-up; a failed scan is logged, "Not a fatal error" (`SUPlainInstaller.m`). Sparkle also releases the new bundle from quarantine. So Sparkle updates of a self-signed app are not blocked by this step.
- Key rotation (docs): rotation is possible "if you both code-sign your application with Apple's Developer ID program and include a public EdDSA key"; with `SUVerifyUpdateBeforeExtraction`, "changing your EdDSA keys can only be done if the update archive is a Developer ID code signed disk image". The pre-extraction fallback in the source is Developer-ID-only ("As fallback for key rotation, check if the archive is Developer ID signed with a team ID that matches the host"). For a self-signed app: the EdDSA key effectively cannot be rotated once `SUVerifyUpdateBeforeExtraction` / `SURequireSignedFeed` are on; without them it can be rotated only while the certificate DR still matches (INFERENCE). Losing the EdDSA private key without Developer ID = no way to update existing installs.

**Info.plist keys** (https://sparkle-project.org/documentation/customization/):
- `SUFeedURL`; `SUPublicEDKey`; `SUEnableAutomaticChecks` (unset = the user is asked on the second launch; `SUPromptUserOnFirstLaunch` moves the question to the first launch); `SUScheduledCheckInterval` default 86400 s, minimum 1 hour; `SUAutomaticallyUpdate` default NO (silent download and install); `SUAllowsAutomaticUpdates`; `SUEnableSystemProfiling` default NO; `SUShowReleaseNotes` default YES.
- `SUVerifyUpdateBeforeExtraction` — added in 2.7.3, requires EdDSA.
- `SURequireSignedFeed` — added in **2.9**; requires `SUVerifyUpdateBeforeExtraction`; appcast and release notes must be signed (`sign_update` on the appcast; `generate_appcast` does it). `SUSignedFeedFailureExpirationInterval` default 20 days (failsafe). `SURequireFeedBundleIdentifier` — 2.11 beta, with a `sparkle:bundleIdentifier` element.

**Publishing** (https://sparkle-project.org/documentation/publishing/):
- Archives: "Put a copy of your .app (with the same name as the version it's replacing) in a .dmg, .zip, .tar.*, or .aar." DMG is a supported enclosure ("APFS formatted images that use lzfse compression are recommended"; add an `/Applications` symlink). Zip: `ditto -c -k --sequesterRsrc --keepParent MyApp.app MyApp.zip`. - `generate_appcast <dir>`: "Signatures are automatically generated ... This is the recommended method." - Release notes: `<sparkle:releaseNotesLink>` (localised with `xml:lang`) or embedded `<description>`; plain text "As of Sparkle 2.4" (`sparkle:format="plain-text"`); **Markdown "As of Sparkle 2.9 and macOS 12"** (`<description sparkle:format="markdown">`); `generate_appcast` picks up `.html` files next to the archive and `.md` files since 2.9; `sparkle:fullReleaseNotesLink` for the full history.
- Channels: `<sparkle:channel>beta</sparkle:channel>` on an item; "By default, updaters only look for updates that are on the default channel"; opt in with `allowedChannels(for:)` -> `Set<String>` ("The default channel is always included in the allowed set"); "an updater cannot exclude itself from the default channel". One appcast can therefore carry stable and beta. — also https://sparkle-project.org/documentation/api-reference/Protocols/SPUUpdaterDelegate.html
- Also: `sparkle:minimumSystemVersion`, `sparkle:hardwareRequirements` (`arm64`, 2.9+), phased rollout (7 groups), critical and informational updates.

**Appcast hosting.** Sparkle's docs do not discuss GitHub. ## 6. Alternatives to Sparkle

- **Hand-rolled updater** (GitHub Releases API + download + replace): no primary guidance exists. It must reimplement what Sparkle does (signature check independent of TLS, atomic replace of a running bundle, quarantine handling, relaunch, translocation); Sparkle had several security fixes in exactly this code in 2026 (2.9.5, 2.9.6). Stats does this (its README: update checks use api.mac-stats.com with api.github.com as fallback).
- **Homebrew cask**: Homebrew 5.0.0 (2025-11-12): "Casks without codesigning are deprecated", "We will disable all Homebrew/homebrew-cask casks that fail Gatekeeper checks in September 2026.", "`--no-quarantine` and `--quarantine` flags have been deprecated", "Homebrew does not wish to easily provide circumvention to macOS security features." — https://brew.sh/2025/11/12/homebrew-5.0.0/ . Current policy: "On macOS, apps, installers and other executable artefacts that Gatekeeper can assess must pass" and "must not require System Integrity Protection or Gatekeeper to be disabled or bypassed." — https://docs.brew.sh/Acceptable-Casks . So the official cask repository is closed to a self-signed, un-notarized app. Whether the September 2026 disable ran exactly on schedule: **UNVERIFIED** (only secondary reports, e.g. a TomatoBar issue). An own tap (`brew install --cask owner/tap/app`) is still possible; AeroSpace does that and removes quarantine in its cask. Notability rules also apply to the official repository.

## 8. Versions

- SemVer 2.0.0 (https://semver.org/): "Major version zero (0.y.z) is for initial development. Anything MAY change at any time." "A pre-release version MAY be denoted by appending a hyphen and a series of dot separated identifiers"; "Pre-release versions have a lower precedence than the associated normal version." Example: "1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-alpha.beta < 1.0.0-beta < 1.0.0-beta.2 < 1.0.0-beta.11 < 1.0.0-rc.1 < 1.0.0". Numeric identifiers compare as numbers, so `0.9.0-beta.1 < 0.9.0-beta.2 < 0.9.0-beta.10 < 0.9.0-rc.1 < 0.9.0`. Use `beta.N` with a dot (not `beta10`, which compares as text). "Build metadata MUST be ignored when determining version precedence."
- `CFBundleVersion`: "This key is a machine-readable string composed of one to three period-separated integers, such as 10.14.1. The string can only contain numeric characters (0-9) and periods." "You can include more integers but the system ignores them." "For macOS apps, increment the build version before you distribute a build." — https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion . So `0.9.0-beta.1` cannot be a `CFBundleVersion`; use one monotonically increasing integer build number (for example the CI run number or a commit count) for every build, beta or stable. `CFBundleShortVersionString` formally has the same three-integer format in Apple's docs (not re-fetched: **UNVERIFIED**); outside the App Store nothing enforces it, and many Sparkle apps show "0.9.0-beta.1" there.
- Sparkle: `sparkle:version` = `CFBundleVersion` (machine version, compared), `sparkle:shortVersionString` = display version. `SUStandardVersionComparator`: "It's 'dumb' in that it does essentially string comparison, in components split by character type."; "These version strings should be in the format of x, x.y, or x.y.z where each component is a number."; "These versions that are compared correspond to the CFBundleVersion values of the updates." — https://github.com/sparkle-project/Sparkle/blob/2.x/Sparkle/SUStandardVersionComparator.h . Sparkle does not compare SemVer pre-release tags; ordering between a beta and the final release comes only from the build number, and beta visibility comes only from `sparkle:channel`.
