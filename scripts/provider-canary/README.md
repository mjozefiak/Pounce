# scripts/provider-canary

Manual isolation and timing canary for the Claude Code CLI as a meeting-notes provider (spec
`.ai/specs/2026-11-10-external-ai-providers.md`, section "Kanarek izolacji", steps 0.1 and 0.2; result in
`docs/decisions/0011-external-providers.md`). **Nothing in the app, the build or CI calls it.** Python 3 standard
library only; run with `python3 -I` from a copy of the script (or `python3 scripts/provider-canary/canary.py`).

Tests of the script (no real CLI, a fake one, a fake home): `python3 -I -m unittest discover -s scripts/provider-canary`.

## What it touches of yours (read this first)

- **The default run never loads your own Claude Code settings, hooks, MCP servers or plugins.** Every call that uses
  your real login carries the isolation flags (`--setting-sources ""`, `--strict-mcp-config`, `--tools ""`,
  `--disable-slash-commands`, `--no-session-persistence`); `require_isolated` refuses, before the process starts, an
  argv that lacks one. The only calls with your real `HOME` and without the flags are `claude --version` and
  `claude auth status` (no prompt, no session; `require_no_content` refuses any other command, and
  `userConfig.noContentCommands` shows that they run no hook, MCP server or plugin). Every other call made *without*
  those flags (the sensitive controls of `userConfig`) runs in a temporary `HOME` that the script builds and deletes.
  The CLI is not logged in there, so those calls end with "Not logged in" and use nothing of the subscription.
- The CLI itself still reads your login and its own state in your config directory (`~/.claude`,
  `~/.claude.json`), as it does for any call. The script writes nothing there.
- **`--positive-control-real-config` (off by default) is the exception. WARNING: it runs your real hooks.** It adds
  ONE pair of calls (step `realConfig`): the same synthetic probe with your real `HOME` without the configuration
  flags (your hooks, MCP servers, plugins, skills and slash commands load) and with the product flags. Both keep
  `--no-session-persistence` and `--tools ""`, so no session is saved. The report holds counts only (hooks started by
  event, user-tier hook modules, MCP servers, plugins, skills, slash commands, agents, tools). The script reads no file
  content in your config directory: it compares names and times before and after, prints what is new or changed to
  stderr, and deletes nothing. It runs only as `--only realConfig --positive-control-real-config` (the script refuses it
  next to any other step), so that the `disk` step (which searches changed files for the run's random markers) does
  not run after it. Use it only if you accept that. The
  first version of this script ran two such calls on every full run; that is how the owner's real hooks ran during
  the first measurement (ADR 0011, "What the first run did"). The first result of the pair is in ADR 0011,
  "Follow-up of 2026-11-20".
- The disk scan (`disk`) walks your config directory, `~/.cache`, the system temp directory and the
  `~/Library/{Caches,Application Support,Logs}` folders whose name contains `claude` or `anthropic`. It only searches
  files modified since the start for this run's random markers and reports paths and counts. It prints no file
  content and changes nothing.
- The temporary work directory (`$TMPDIR/provider-canary-*`) is removed at the end, also when a step raises or the
  script gets Ctrl-C, SIGTERM or SIGHUP; a `claude` process still running then is killed with its process group
  first (it runs in its own session, so the terminal's Ctrl-C does not reach it).

## What it sends

Only synthetic text generated by the script, with a random canary marker (`LCANARY-<hex>`) per call. The report holds
flag names, exit codes, timings, token counts, paths and counts. It never holds a marker, a prompt, a model answer or
stderr text; a failure line is cut to 160 characters and stripped of addresses, tokens and the home path (CLI error
lines, not model output). The script asserts that no marker is in the report before it writes it.

## Run

```sh
python3 scripts/provider-canary/canary.py --out /tmp/canary.json          # about 9 short logged-in calls and one of 40 000 tokens
python3 scripts/provider-canary/canary.py --only userConfig               # no model call: user-level hooks, MCP, plugins, session files
python3 scripts/provider-canary/canary.py --only userConfig,isolation,hooks,disk   # the isolation proof: 2 short model calls
python3 scripts/provider-canary/canary.py --no-calls                      # offline checks only (locator, env, TCC probe)
python3 scripts/provider-canary/canary.py --only isolation,disk --out ...  # a subset; --merge-into <report> to add to one
python3 scripts/provider-canary/canary.py --large-tokens 100000 --only timings   # the Q12 budget (about 140 000 real tokens)
```

`--model` (default `sonnet`) is used for the timing calls, `--cheap-model` (default `haiku`) for everything else.
The child gets the environment allowlist of the spec plus `USER` (the Keychain login is found by it; without it
`claude -p` answers "Not logged in"). It is run in its own process group with an empty temporary directory as
the working directory and a private `TMPDIR`.

## Checks (spec table, numbers as in the report)

| Spec # | Step | How |
|---|---|---|
| 1 | File tools | `isolation`: decoy project, prompt asks to read a file outside the working directory; flags `--tools ""`. |
| 2 | Shell | Same call asks to run `touch <marker file>`. |
| 3 | Hooks, project level | A project hook in the decoy writes a marker file. `hook-project` must not appear, and the stream must report 0 started hooks (`--include-hook-events`). |
| 3 | Hooks, MCP and plugins, **user level** | `userConfig`: a temporary `HOME` with a synthetic user configuration: command hooks for SessionStart, UserPromptSubmit, Stop and SessionEnd in `settings.json`, an MCP server in `.claude.json`, an enabled plugin with a SessionStart hook, an agent definition. Each one creates an empty marker file when the CLI runs it. Six cases: `control` (no flag: everything must fire, or the test proves nothing), `product` (the product flags: nothing may fire) and each flag alone (`--setting-sources ""`, `--strict-mcp-config`, `--safe-mode`, `--no-session-persistence`). No login there, so no model call; the Stop hook is not reached. |
| 3 | Hooks under the real login | `hooks` (`hookEvents`): one call with the real `HOME` and the product flags plus a canary hook passed by `--settings` (UserPromptSubmit and Stop; the product never passes `--settings`). The canary hooks must fire (the detector works through the end of the turn) and `hooksStartedBeyondCanary` must be 0: any other started hook would be one of yours. The debug log's hook modules are counted by tier (user tier must be 0). |
| 4 | `CLAUDE.md`, MCP, plugins | The decoy has a `CLAUDE.md` with a token and a `.mcp.json` whose server is `touch <file>`. The init event reports tools, MCP servers, skills and plugins (`pluginsNotBuiltIn` must be 0). |
| control | Positive control with the real config, **opt-in** | `realConfig`, only with `--positive-control-real-config` (see the warning above): one call without the configuration flags and one with the product flags; counts of hooks started, user-tier hook modules, MCP servers, plugins, skills, slash commands, agents and tools; the config directory compared by name and time. Without it, the tool, shell and `CLAUDE.md` results rest on the init event (`tools` is empty). |
| safe-mode | `--safe-mode` | `safeMode`: the product flags with and without `--safe-mode` under the real login (login, JSON result shape, init counts, hook modules by tier). Recommended only if the login and the format are unchanged and something less is loaded. |
| 5 | TCC | `tccInheritance`: opens two TCC-protected files from the script and from a plain child. See below. |
| 6 | Session files | `userConfig`: after each case the temporary config directory's `projects/**/*.jsonl` is searched for that call's marker: 1 file without `--no-session-persistence`, 0 with it. `disk` does the same search in the real config directory for every isolated call (`sessionFilesWithMarkerByIsolatedCall`, all 0). Paths and counts only. |
| 6 | Copies on disk | `disk`: every file modified since the start under the CLI config directory, `~/.claude.json`, `~/.cache`, the system temp directory, `~/Library/{Caches,Application Support,Logs}/*claude*|*anthropic*`, the child `TMPDIR` and working directories is searched for each call's marker. Report: paths and counts. |
| 7 | Login | `auth`: `claude auth status` (only `loggedIn`, `authMethod`, `apiProvider` are kept; the e-mail is dropped), the same under an empty config directory and an empty `HOME`, with one short call each. |
| 0.2 | Timings | `timings`: a tiny call, about 3 000 tokens in Polish and English, and one large call (default 40 000 estimator tokens); wall time, `duration_api_ms`, reported tokens, ratio to the app's estimator. |

| 0.2 | Failures | `failures`: unknown model, unknown flag, SIGTERM to the process group during generation (exit code, time to exit, leftover processes). |

## TCC inheritance (check 5): what the script can and cannot show

The script opens `~/Library/Safari/Bookmarks.plist` and `~/Library/Messages/chat.db` (open only, nothing is read) from
itself and from a plain child process, and reports `open` or the errno. If the terminal running it has no Full Disk
Access both fail with errno 1 and nothing is learned about inheritance. **Not shown by the script:** whether a child
of `Lintel.app` with Full Disk Access (the real case) is allowed through. Procedure for the owner:

1. Grant Full Disk Access to the terminal app that runs the script (System Settings, Privacy and Security) and run
   `canary.py --no-calls`. If the parent shows `open` and the plain child shows `open`, a child inherits the
   permissions of its responsible process on this Mac.
2. For Lintel itself: with the debug build `dist/Lintel-QA.app` holding Full Disk Access, start a child through the app
   (when the provider code exists: PR 2) and repeat the probe from that child. Until then the ADR treats a child of
   Lintel as holding Lintel's permissions, and relies on the proven absence of tools and hooks (the spec's option (a)).
3. Revoke the grant again afterwards.
